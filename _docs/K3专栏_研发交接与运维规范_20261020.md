# 一、交接说明

## 1.1 这是什么

K3 专栏是 Creality K3 单机型的用户反馈看板，一个自包含的静态 HTML 页面，数据由脚本从公开渠道采集后内联进页面。

| 项 | 说明 |
|---|---|
| 交付物 | `creality-k3.html`（单文件，560 KB，数据内联，零外部依赖） |
| 当前形态 | GitHub Pages 静态托管 |
| 目标形态 | 内网服务器挂载，由研发接手后续维护 |
| 当前基线 | 2026-10-20：422 条 / 13 个站点 / 5 个采集批次 / 发布日 2026-08-27 ~ 2026-10-19 |

## 1.2 你接手的是三件事

| # | 事项 | 频率 | 说明 |
|---|---|---|---|
| 1 | **数据更新** | 每工作日 | 跑采集 → 标注 → 注入 → 校验 → 发布 |
| 2 | **页面维护** | 按需求 | 改版式、加面板、调交互（口径不能随意动，见第十章） |
| 3 | **故障处理** | 按需 | 源站改版、限流封禁、采集产出异常 |

## 1.3 先读这几节

如果只有十分钟，读这四处就够判断能不能接：

- **2.2 部署形态** —— 内网无外网时采集与展示必须分离

- **6.2 一次采集的六步** —— 抓取逻辑的总纲，后面 6.3~6.9 都是它的展开
- **11.2 故障排查表** —— 已知的坑都在这儿

# 二、系统架构

## 2.1 三条链路

```
【采集】 _k3_collect_channels.py   →  _k3_candidates_YYYYMMDD.json   （主条目：帖子 / 视频 / 图文）
         _k3_collect_comments.py   →  评论候选（过质量闸门后才进）    （挂在主条目下的评论 / 评价）
                    ↓ 人工/Agent 标注（情感、维度、问题点、摘要、译文）
【写入】 _k3_inject_candidates.py   →  creality-k3.html 内的 K3_FEEDBACK_DATA
                    ↓
【发布】 校验脚本 → 静态托管
```

关键设计：**采集器不直接写页面**。情感、维度、问题点是判断而不是抽取，自动猜会把噪声写成结论。所以中间必然有一步标注。

两条采集支路的分工：主条目靠**关键词搜索**发现内容，评论靠**已入库的主条目**反向抓取。内部逻辑见第六章。

## 2.2 部署形态

这是接手后第一个要决策的点，**推荐模式 A**。

| | 模式 A：采集与展示分离（推荐） | 模式 B：单机 |
|---|---|---|
| 拓扑 | 采集机（可出外网）→ 文件同步 → 展示机（内网） | 一台机器同时跑采集与托管 |
| 前提 | 展示机只需能被内网访问 | 该机器必须有外网出口 |
| 风险 | 需要一条同步通道 | 内网服务器通常不给外网出口，容易卡住 |
| 适用 | 绝大多数企业内网环境 | 机器本身有出口，或走代理 |

模式 A 的同步对象只有**一个文件**（`creality-k3.html`），用 rsync / scp / 共享盘 / 内网 Git 都可以，无需数据库或接口。

如果后续要做「内网多人看板 + 权限」，再考虑把 HTML 放进内网的静态站点服务，仍是静态文件，不涉及后端。

## 2.3 页面为什么适合内网

已实测：页面内**没有任何 CDN、外部 JS/CSS、字体链接或远程接口**。所有 `https://` 出现处都是数据条目里的原文链接（YouTube / B站 / Reddit 等）。

含义：

- 内网无外网时，页面**完整渲染，功能不受影响**
- 唯一影响是「原文 ↗」按钮点不开（见 5.4 的处理建议）

这一点是刻意保持的，后续改版**不要引入任何外部资源**（CDN 图表库、在线字体、外链图标），否则内网会白屏。

# 三、环境与依赖

## 3.1 服务器要求

| 项 | 要求 |
|---|---|
| 系统 | Linux（x86_64），Windows Server 亦可 |
| 运行时 | Python 3.9+（实测 3.13）；Node.js 16+（仅校验脚本用） |
| 内存 | 采集脚本峰值 < 200 MB |
| 磁盘 | 数据与日志 < 1 GB/年 |
| 依赖库 | **无第三方依赖**，全部为 Python 标准库；Node 只用内置 `vm` / `fs` |

**没有 requirements.txt 也不需要**：脚本只用到 `urllib` / `json` / `ssl` / `re` / `xml` / `html` 等标准库。部署时不需要 `pip install`，也不需要 `npm install`。

## 3.2 网络出口

| 用途 | 是否需要外网 |
|---|---|
| 采集（B站 / YouTube / Reddit / 论坛 / 媒体） | **必须** |
| 标注、注入、校验、页面渲染 | 不需要 |
| 展示 | 不需要 |

采集脚本会主动**清空代理环境变量**（`ENG.clear_proxy()`）走直连。如果服务器必须经代理出网，这一处要改，否则会连不上。

实测被限制的源站：

- Reddit：仅 `search.rss` 可用，间隔需 ≥6.5 秒；`.json` 与 OAuth 通道在部分出口 IP 上直接 403
- B 站：必须先取 cookie 预热，否则第二次请求起 412（见 11.2）

## 3.3 敏感文件

| 文件 | 内容 | 处置 |
|---|---|---|
| `_k3_creds.json` | YouTube API Key、Reddit OAuth 凭据 | **禁止入库、禁止放页面、禁止进 Git**；部署时单独投放、单独授权 |
| `k3_feishu_pushed.json` | 飞书推送登记（含时间戳） | 运行态文件，不入库 |
| 内网发布凭据 | 替换原 GitHub PAT | 用部署令牌或 SSH key，按月轮换 |

## 4.3 页面与构建（重要差异）

**K3 页面不走构建器。** 这一点与另两个专栏不同，接手时最容易误判：

| 页面 | 构建方式 | 维护方式 |
|---|---|---|
| `creality-k3.html` | 手写整页 + 脚本注入数据 | 直接改 HTML 结构 / 跑注入脚本改数据 |
| `software-columns.html` | `_build_column.py` + `_col_shell.html` | 改壳 → 重新构建 |
| `creality-mbox.html` | 同上 | 同上 |

因此：

- 改 K3 的**版式与交互**要直接编辑 `creality-k3.html` 里的 `<style>` 与 `<script>`
- 改 K3 的**数据**必须通过 `_k3_inject_candidates.py`，不要手工编辑 `items` 数组
- `_nav.html` 是三个页面共用的侧栏源，改导航要改它再重新构建另两页（K3 的侧栏由构建器一并同步）

# 五、部署到内网服务器

以下按模式 A（采集与展示分离）、Linux + nginx 编写。用 Windows Server 时把 nginx 换成 IIS、cron 换成计划任务即可。

## 5.1 目录规划

```
/opt/k3-feedback/
├── app/                     # 展示机：只放页面
│   └── creality-k3.html
├── deploy/                  # 采集机：脚本与数据
│   ├── _k3_*.py / _k3_*.js
│   ├── _k3_creds.json       # 单独授权，600
│   ├── candidates/          # 候选池归档
│   └── logs/
└── backup/                  # 每次发布前的页面备份
```

## 5.2 部署步骤

1. 展示机建目录，把 `creality-k3.html` 放进去，属主设为 web 用户
2. 采集机建目录，投放脚本与凭据（凭据 `chmod 600`）
3. 采集机手工跑一次 `python _k3_collect_channels.py --days 3`，确认能出候选池
4. 展示机配 nginx（见 5.3），确认内网能打开
5. 配定时任务（见 6.11）
6. 手工完整跑一遍五步流水线，确认页面更新且校验全绿
7. 建立发布前备份：每次覆盖前把旧页面拷到 `backup/`，保留 30 天

## 5.3 访问控制

内网也需要基本鉴权，避免链接被转发出去。nginx 最小配置：

```nginx
server {
    listen 80;
    server_name k3-feedback.internal;

    root /opt/k3-feedback/app;
    index creality-k3.html;

    auth_basic "K3 Feedback";
    auth_basic_user_file /etc/nginx/.htpasswd;

    # 单文件页面，禁缓存便于发布后立即生效
    location = /creality-k3.html {
        add_header Cache-Control "no-cache, must-revalidate";
    }
}
```

若要接公司 SSO，把 `auth_basic` 换成对应的 `auth_request` 网关即可，页面本身不需要改。

## 5.4 外链与内网的关系

页面里每条反馈都有「原文 ↗」按钮，指向 YouTube / B站 / Reddit 等外部站点。

**内网用户点击会打不开**。这不是 bug，是网络边界导致的。三个处理选项：

| 选项 | 做法 | 取舍 |
|---|---|---|
| 保持现状 | 不做处理，在页面说明里注明「原文需在可访问外网的设备打开」 | 零成本，但每次都要解释 |
| 数据镜像 | 采集时把原文正文完整入库（原文字段已有），弱化外链依赖 | 推荐；正文本来就在页面上，链接只是溯源 |
| 统一跳板 | 外链统一替换为内网跳板服务 | 需要额外开发，除非有现成网关 |

**建议不要在页面里写死内网不可达的提示**，因为同一份页面可能同时给内外网用；说明放在部署文档里即可。

# 六、数据抓取逻辑与更新链路

本章是接手后的核心。**6.2~6.9 是采集器内部怎么判断、怎么过滤**，6.10 之后才是每天要敲的命令。

如果只想知道「跑一条命令会发生什么」，直接读 6.2 的六步表和 6.8 的候选池结构。

## 6.1 三层窗口

| 层 | 触发 | 窗口 | 目的 | 产出 |
|---|---|---|---|---|
| L1 每日增量 | 每工作日 | T-1（主）+ T-2（兜底） | 当天新发布的实测、短评、追评 | 3~8 条/天 |
| L2 每周回捞 | 仅周一 | T-7 | 审核延迟上架的电商评价、被顶起的老帖 | 0~10 条/周 |
| L3 月度校准 | 每月 1 日 | 近 90 天全量 | 修正错标、补字段、清死链、重算口径 | 全量 |

首发期（2026-10 ~ 11）L1 放宽到 T-3，样本稀疏期宁多勿漏；2026-12 起回到 T-1/T-2。

**不要改成每日全量**，原因：成本随样本线性增长；同一条内容今天判负面、明天判中性会导致趋势不可比；源站改标题删帖会破坏已确认条目。

## 6.2 一次采集的六步

`main()` 的编排固定六步，顺序不能换（越靠前越便宜，后面的步骤依赖前面的结果）。

| 步 | 做什么 | 实现 | 输出去向 |
|---|---|---|---|
| ① | 分渠道采集 | `collect_bili` / `collect_youtube` / `collect_forum` / `collect_reddit*` | `cands[]` |
| ② | 丢机器数据帖、官方纯营销帖 | `is_junk()` / `is_official_ad()` | `dropped[]`（带原因） |
| ③ | 跨帖 / 跨版镜像归并 | `merge_mirrors()` | 主条 `mirrors[]` |
| ④ | 信号门槛 | `--min-signal` | `dropped[]`（`low-signal`） |
| ⑤ | 与页面存量做双线差集 | uid 一条线 + 归一化 URL 另一条线 | `dupWithPage` 标记 |
| ⑥ | 写候选池 | 排序后落盘 | `_k3_candidates_YYYYMMDD.json` |

三个开关决定这次跑多宽：

| 参数 | 默认 | 作用 | 日更怎么用 |
|---|---|---|---|
| `--days` | 45 | 发布日窗口天数，0 = 不限 | 日更 3 / 周一 7 / 月度 90 |
| `--min-signal` | `mid` | `low` 全留、`mid` 去纯开箱与转链、`high` 只要实测 | 日更 `mid`，月度 `low` |
| `--only` | `all` | `bili` / `youtube` / `forum` / `reddit` | 单渠道排障时用 |

**核心纪律：采集器从不产出「已判定的情感」。** 它只负责找到内容、归一化、去重、打信号等级；`sentiment` / `dimensions` / `problemPoints` 全部留给标注。情感和问题点是判断不是抽取，自动猜会把噪声写成结论——这就是链路中间必须有一步标注的原因。

### 6.2.1 窗口判定 `in_window()`

三个分支，都不容商量：

```python
def in_window(published, days):
    if not published: return False        # 拿不到发布日 → 不入库
    if days <= 0:     return True          # --days 0 表示不限
    ...                                    # 日期解析失败 → 不入库
    return (TODAY - d).days <= days
```

**拿不到发布日的一律不入库**：没有发布日，既不能证明它在窗口内，也不能证明它是新的。

## 6.3 第一步：四个渠道的采集与相关性闸门

四个渠道的接口、查询词、限速、相关性判据各不相同，**不能合并成一类处理**。共同点是「k3 字面命中 + 打印机语境命中」双条件缺一不可。

### 6.3.1 B 站（`collect_bili`）

| 项 | 值 |
|---|---|
| 前置 | 必须先 GET `https://www.bilibili.com/` 拿 `buvid3` / `b_nut` cookie（`BILI_WARMUP`），否则第 2 次请求起必返回 **-412** |
| 接口 | `api.bilibili.com/x/web-interface/search/all/v2`，每页 20 |
| 查询词 | `创想三维 K3` / `Creality K3` / `K3 换头` / `K3 四喷嘴` / `K3 多色打印` |
| 请求间隔 | warmup 后 1.2s；关键词之间 2.0s |
| 相关性 | `"k3" in text` **且** 命中 `BILI_CTX` 任一语境词 |

`BILI_CTX`（14 个）：`创想` / `creality` / `klitek` / `喷嘴` / `nozzle` / `多色` / `multicolor` / `换头` / `换色` / `3d打印` / `打印机` / `3d printer` / `四喷嘴` / `挤出`

为什么两道闸：搜 `K3` 会带出火车头、音乐、游戏内容，只看「有没有 k3 字面」等于没筛。

### 6.3.2 YouTube（`collect_youtube`）

| 项 | 值 |
|---|---|
| 前置 | 需 `_k3_creds.json` 的 `youtube.apiKey`；**缺失则整渠道跳过**（`code: NO_KEY`），不算失败 |
| 接口 | YouTube Data API v3 `search` |
| 查询词 | `Creality K3` / `Creality K3 review` / `Creality K3 multicolor` / `KliTek` / `Creality K3 unboxing` |
| 相关性 | `"k3" in text` **且** 命中 `YT_CTX` 任一语境词 |

`YT_CTX`（15 个）：`creality` / `klitek` / `创想` / `nozzle` / `printer` / `printing` / `multicolor` / `多色` / `tool chang` / `换头` / `3d print` / `3d打印` / `filament` / `unboxing` / `开箱`

### 6.3.3 Creality 官方论坛（`collect_forum`）

| 项 | 值 |
|---|---|
| 接口 | Discourse `/tag/<tg>.json`，另用 `/latest.json?page=1` 兜底补关键词命中 |
| 标签 | `k3` / `cfs` / `multicolor` / `multihead` |
| 请求间隔 | 1.5s（`FORUM_RATE_SEC`） |
| 相关性 | **只认标题里明确出现 `K3` / `KliTek` / `Kli Tek`**（`FORUM_K3_RE`） |

🔴 **这是最容易踩的坑：`CFS` 和 `multicolor` 标签本身不构成 K3 证据。**

CFS 是 K1/K2/K3 通用的供料系统，`cfs` 标签下 30 帖里绝大多数是 K2 Plus / K1 Max 的故障；`multicolor` 标签里也有「Feature Request: Skip unnecessary CFS tool changes」这类跨机型需求。靠标签收会把 K1/K2 的问题算进 K3。

K3 的量本来就少（`k3` 标签全历史 4 帖），**宁可少收也不能错收**——错收会直接污染问题点结构，而问题点结构是这份看板的主要结论。产出约 0~3 条/周，定位是长期基建而非日常主力。

### 6.3.4 Reddit（`collect_reddit` / `collect_reddit_oauth`）

| 项 | 值 |
|---|---|
| 通道优先级 | 有 `clientId` + `clientSecret` → OAuth；换 token 失败或无凭据 → 退 RSS |
| 接口 | RSS `search.rss`（`.json` 与 OAuth 在部分出口 IP 上直接 403） |
| 查询 | `Creality K3` / `KliTek` / `Creality K3 review`（全站搜索）+ `r/Creality`、`r/3Dprinting`（版内搜 K3） |
| 请求间隔 | **6.5s**（`REDDIT_RATE_SEC`）；429 后退避 20s（`REDDIT_BACKOFF`）——10s 不够，实测会连挂 |
| 去样板 | `clean_reddit_title()` 去掉 RSS 标题尾部 `submitted by /u/x to r/y` |

**四道相关性闸门**（`reddit_relevant`），缺一不可：

```python
if "k3" not in s and "klitek" not in s:            return False  # ① 字面
if not REDDIT_PRINTER_RE.search(s):                return False  # ② 打印机语境
if REDDIT_OFFTOPIC_RE.search(s) and not REDDIT_BRAND_RE.search(s):
                                                   return False  # ③ 排除同名异物
if not re.search(r"\bk3\b|klitek", (title + body[:200]).lower()):
                                                   return False  # ④ 必须真的在谈 K3
```

每一条都是踩出来的，不是理论防御：

| 闸门 | 挡的是什么 | 实测案例 |
|---|---|---|
| ② `REDDIT_PRINTER_RE` | 只有 k3 字面的无关帖 | `r/3Dprinting` 的「Cool diy printers」正文偶现 k3 被命中 |
| ③ `REDDIT_OFFTOPIC_RE` | **同名异物** | `Kimi-K3` 让 `r/LocalLLaMA`、`r/GeminiAI` 的 LLM 讨论被当成 K3 打印机 |
| ④ 标题或正文前 200 字 | 顺带提及 | 「A 和 K3 怎么选」这类竞品比较可以收，正文里偶然带一句的不收 |

### 6.3.5 四渠道一览

| 渠道 | 窗口内产出 | 失败是否阻塞 | 主要失败模式 |
|---|---|---|---|
| B 站 | 视频 + 图文 | 否 | 412（无 cookie）/ 搜索接口限流 |
| YouTube | 视频 | 否 | 无 apiKey 直接跳过 / 配额耗尽 |
| 官方论坛 | 帖子 | 否 | 站点改版 / 标签页 404 |
| Reddit | 帖子 | 否 | **出口 IP 被封锁（403/429）——已知，不当告警** |

任一渠道挂掉都不影响其他渠道和整体链路。这是刻意的：`errors[]` 只记录，不中断。

## 6.4 第二步：噪声过滤

`is_junk()` 挡机器数据，`is_official_ad()` 挡官方营销。两者都在归并之前跑，因为机器数据帖的正文会让镜像归并误判。

| 判据 | 实现 | 实测来源 |
|---|---|---|
| 机器数据帖 | 标题匹配 `^(sweep\|dump\|archive\|backup\|log)\b` **且**含 `\d{4}-\d{2}-\d{2}`；或正文含 `H4sIA`（gzip+base64 头）；或正文有 80+ 连续无空白串（`has_blob`，含 `://` 的 URL 除外） | `r/lineup_sweep` 类自动化账号的 `sweep 2026-10-08 part 2/3`，正文是 base64 压缩块，块内随机出现 `k3` 而被关键词命中 |
| 官方纯营销 | `sourceType == "官方"` **且** 标题命中 `OFFICIAL_AD_RE`（`creator spotlight` / `feel the power` / `white whale` / `pre-order go live` / `more tricks up its sleeve` / `welcome to creality official`） | CREATOR SPOTLIGHT 系列、悬念营销、抽奖、预售预告——是品牌宣传不是用户反馈 |

两个概念别改混：

- **官方号发布的真实反馈性内容** → 保留，标 `sourceType=官方`，口径上单列（见第十章）
- **官方号的纯营销帖** → 在这里就丢，它连「用户说了什么」都不算

丢掉的东西不消失，`dropped[]` 里带原因留存：

```json
"dropped": [ { "title": "...", "sourceLink": "...", "reason": "machine-blob" } ]
```

### 6.4.1 `guess_source_type()` 只做启发式

```python
_OFFICIAL_RE_REDDIT = r"^/?u/creality"                             # 实测 /u/Creality_3D、/u/Creality_Cloud
_OFFICIAL_RE_BILI   = r"^创想三维|creality\s*官方|官方\s*creality"   # 实测「创想三维Creality」
```

**只识别「明确是官方号」，其余一律留空交标注环节。** 自动判可信度一定会误杀，所以不做。

同理，带货号（`榜单` / `推荐官` / `严选` / `团长` / `好物` / `精选` / `种草` / `优惠` / `返现` / `旗舰店` / `导购` / `爆款`）**只打 `marketing-author` 标记，不过滤**——误杀的代价比留着噪声高，是否采信由标注环节定。

## 6.5 第三步：镜像归并

`merge_mirrors()` 把「同一内容跨帖 / 跨版转载」合并成一条，其余写进 `mirrors[]`，**声量只算一次**。

不合并的后果很具体：Creality 一条官方公告会同时发到 `r/Creality`、`r/crealityk3`、`r/Creality_k3`、`r/crealityk1`、`r/Ender3Pro` 等 10 个版块，不合并就是 10 条声量。

匹配规则：

1. `norm_title()` 归一化——去标签、转小写、去所有空白与标点、截 90 字
2. 完全相等 → 合并，`mirrors[]` 追加链接
3. **前缀匹配**：短标题（≥16 字）是另一条的前缀也算同一内容

第 3 条是必要的。实测 `BV1bwpv6MEoa` 与 `BV1nHeu6UEuH` 两个视频标题只差一句「兄弟们，创想三维 K3，新机到手！」，完全相等判不出来。

⚠️ 因此 `clean_reddit_title()` 必须先去掉 `submitted by /u/x to r/y`——两个版块转发同一帖时这段不同，不先去就会归一化成两个标题，镜像合并直接失效（实测踩过 #9/#10）。

## 6.6 第四步：信号门槛

同一次采集里 B 站播放量能跨 4 个数量级（5 ～ 3.0 万）。不分级会把「13 播放的开箱」和「3 万播放 200 小时实测」一视同仁灌进页面。

| 渠道 | high | mid | 依据 |
|---|---|---|---|
| B 站 `signal_bili` | 播放 ≥1000 **或** 评论 ≥30 | 播放 ≥200 **或** 评论 ≥10 | 双指标任一达标即可（小 UP 主实测可能播放低但评论多） |
| YouTube `signal_youtube` | 播放 ≥10000 | 播放 ≥500 | 播放量级差一个数量级 |
| Reddit `signal_reddit` | 正文 ≥200 字 | 正文 ≥60 字 | RSS 不带 score / 评论数，只能用「正文有多少实际表达」代理 |

`--min-signal mid`（日更默认）丢掉 `low`，`--min-signal low`（月度）全留。被丢的进 `dropped[]` 的 `low-signal`，月度 L3 还能捞回。

## 6.7 第五步：与页面差集（双线）

不是按发布日筛，而是**跟页面已有条目比**。两条线并行，任一条命中即标重复：

| 线 | 键 | 覆盖什么 |
|---|---|---|
| 主 | `uid = sha1(归一化URL + "\|" + 归一化 originalText[:200])[:16]` | 主键，精确 |
| 兜底 | `norm_url(sourceLink)` | URL 同但正文被改过（`originalText` 变了 uid 就变） |

命中后写 `dupWithPage: "uid"` 或 `"url"`，仍留在候选池里（便于审计），但 `freshVsPage` 只数没标记的。

🔴 **uid 必须带原文片段。** 一个 URL 承载多条反馈（一个视频页下 20 条评论），只用 URL 计算会静默丢数——这是踩过的坑，不是理论风险。

推论：**禁止改写已有条目的 `originalText`**。改了 uid 就变，同一条会被当成新条目重复入库，或者在差集里消失。

## 6.8 候选池结构

产物 `_k3_candidates_YYYYMMDD.json`，排查时主要看这四个字段：

```json
{
  "generatedAt": "2026-10-20 03:31:07",
  "windowDays": 3,
  "windowFrom": "2026-10-17",
  "counts": {
    "rawFetched": 128,     // 四渠道共抓到多少（未过滤）
    "junkDropped": 41,     // 机器数据 + 官方营销 + 低信号，合计
    "mirrorsMerged": 7,    // 被合并掉的镜像条数
    "candidates": 80,      // 归并后剩余
    "freshVsPage": 6,      // 真正新增（差集后）
    "dupByUid": 71,
    "dupByUrl": 3,
    "pageTotal": 422
  },
  "sources": [ ... ],      // 每个查询的 HTTP 码与接受条数
  "errors":  [ ... ],      // 采集失败明细
  "dropped": [ ... ],      // 丢弃明细 + 原因
  "items":   [ ... ]       // 候选条目（含 uid / dedupKey / signal / dupWithPage）
}
```

**排查口径**：`rawFetched` 正常但 `freshVsPage` 为 0 → 不是采集坏了，是这几天确实没新内容；`rawFetched` 本身就低 → 去看 `sources[]` 的 HTTP 码和 `errors[]`。

`sources[]` 里每个渠道都有一条记录，`step` 字段能看出走到了哪一步（`warmup` / `rss` / `fallback` / `skip`）。

## 6.9 评论采集的额外闸门

评论是单独一支（`_k3_collect_comments.py`），因为它从**已入库的主条目**出发抓评论，不直接搜关键词。

不加闸门的后果是量化的：全量入库会让页面从 240 KB 涨到 4.8 MB，且 95% 是 "So cool!"。实测保留 YouTube 420 条 / B 站 33 条（B 站仅 9.7%）。

### 6.9.1 质量闸门 `gate()`

顺序固定，**先便宜后贵，命中即返回**（便于审计 `reason`）：

| 顺序 | 判据 | 返回 reason |
|---|---|---|
| 1 | 空 | `empty` |
| 2 | 引流广告（`comment link` / `check my bio` / `telegram` / `t.me/` / `加微信` / `私信我` / 任何 URL） | `spam` |
| 3 | 去表情 / 标点后为空 | `emoji-only` |
| 4 | 中文 <6 字 **且** 总长 <12 字符 | `too-short` |
| 5 | 整条只有赞美词 | `praise-only` |
| 6 | 信息量评分 <1 | `low-info` |
| 7 | 审核档 = 无效 | `review-off-topic` / `review-no-info` |

第 4 条的阈值是标定过的：挡掉 `So cool!`(9)、`Looks good`(10)，但保留 `Is the K3 out?`(14)——**提问本身有信息量**。

第 6 条的信息量评分：

| 加分项 | 分 | 说明 |
|---|---|---|
| 含数字 | +2 | 价格 / 尺寸 / 条数 / 时间，通常有实指 |
| 命中现象或技术词 | +2 | `nozzle` / `clog` / `jam` / `warp` / `层纹` / `翘边` / `换色` / `固件` 等约 70 个 |
| 中文 ≥15 字或英文 ≥40 字符 | +1 | 长评论更可能讲清问题 |
| 对比句（`vs` / `比` / `better than`） | +1 | |
| 纯附和（`我也` / `me too` / `same here`） | −1 | |

🔴 **三个已复发的坑，改这段代码前先看**：

| 坑 | 现象 | 正解 |
|---|---|---|
| 数字误判 | `"3d printer"` 里的 `3` 被当数字 → `"Wow nice 3d printer i dont have one :("` 混进正文 | 判数字前先剔 `\b[234]d\b` / `\b[248]k\b` 及型号 token |
| 泛词加分 | `print` / `printer` / `打印` 几乎每条都有，加分等于没筛 | 归入 `WEAK_WORDS`，**命中不加分** |
| 单字情感词 | `稳` 误判「热床平稳度怎么样」；`差` 命中「差异」 | 情感词表**禁单字** |

### 6.9.2 审核三档（`_k3_review_rules.py`）

| 档 | 含义 | 处置 |
|---|---|---|
| 有效 | 与本机相关且有具体信息 | 进页面，参与情感与问题结构 |
| 泛讨论 | 与本机相关但没具体信息（如「等评测」） | 进页面明细（灰底标记），**数据层直接清空** `problemPoints` / `dimensions` |
| 无效 | 与本机无关 / 无具体信息 | **采集阶段即丢弃**，不写候选池、不进页面 |

定档逻辑：

```python
lvl = relevance(text)        # strong / weak / none
sc  = info_score(text)
if CONTENT_REQ:                  → 泛讨论
if lvl == "none":                → 无效（与本机无关）
if STANCE:                       → 有效（有明确态度表达）
if lvl == "weak" and sc == 0:    → 无效（无具体信息）
if lvl == "strong" and sc >= 1:  → 有效
else:                            → 泛讨论
```

🔴 **规则唯一实现在 `_k3_review_rules.py`，`gate()` / `_k3_audit_comments.py` / `_k3_inject_comments.py` 三处共用，禁止各写一套。** 三处写三个版本一定漂移，漂移后页面数字与引擎数字对不上。

三条硬约束：

1. **相关性只看评论自身文本。** 父标题只能用来补话题，不能补相关性——453 条评论的父标题全是 K3 视频，拿来放行等于 100% 通过。
2. **英文关键词必须加词边界**（`_en_hit` 用 `\b`）。曾出现 `informative` 命中 `rma`、`absolutely` 命中 `abs`，59 条巧合命中。
3. **数字判定前必须剔除型号 token**（`K3` / `K1` / `U1` / `X1C` / `C5` / `3d` / `CFS` / `AMS`）。此坑已复发三次。

另：`guess_lang()` **必须先测假名再判汉字**，否则日语（含大量汉字）会被整体吞成中文。

## 6.10 五步流水线

```bash
# 1. 采集（周一用 --days 7，每月 1 日加 --min-signal low）
python _k3_collect_channels.py --days 3

# 2. 标注：人工或 Agent 补 sentiment / topics / dimensions / problemPoints / summaryCn / translation
#    未标注的宁可跳过，不要猜

# 5. 发布（备份 → 覆盖 → 同步到展示机）
```

## 6.11 定时任务

```cron
# 周一：T-7 回捞。T-7 已覆盖 T-3，所以周一不要再配一条 --days 3，否则同一批内容采两遍
30 3 * * 1    cd /opt/k3-feedback/deploy && python3 _k3_collect_channels.py --days 7 >> logs/collect.log 2>&1

# 周二至周五：T-1/T-2 日更
30 3 * * 2-5  cd /opt/k3-feedback/deploy && python3 _k3_collect_channels.py --days 3 >> logs/collect.log 2>&1

# 每月 1 日 04:00：近 90 天全量校准（含低信号条目）
0 4 1 * *     cd /opt/k3-feedback/deploy && python3 _k3_collect_channels.py --days 90 --min-signal low >> logs/collect.log 2>&1
```

三个任务**按星期互斥**，同一时刻只会跑一条。窗口叠加靠的是「周一放宽到 7 天」，不是「周一跑两遍」。

如果某天漏跑，第二天照常跑当日窗口即可，不需要补跑多天——迟到的内容会由下周一的 T-7 窗口或月度 L3 捞回。

## 6.12 凭据配置

`_k3_creds.json` 结构（**字段名是 camelCase，写错等于没配**）：

```json
{
  "youtube": { "apiKey": "..." },
  "reddit":  { "clientId": "...", "clientSecret": "..." }
}
```

`load_creds()` 的失败策略是「缺文件 / 缺字段一律返回空串，绝不抛错」——采集器据此决定走 OAuth / API 还是退回 RSS / 跳过，保证无凭据也能跑完日更。

所以凭据缺失不会让链路中断，但会少数据：

| 缺失项 | 后果 | 日志里的痕迹 |
|---|---|---|
| `youtube.apiKey` | YouTube 整渠道跳过 | `sources[]` 里 `channel: YouTube, step: skip, code: NO_KEY` |
| `reddit.clientId` / `clientSecret` | 退回 RSS（2026-11-13 后 RSS 可能失效） | `channel: Reddit, step: rss, code: NO_CREDS` |
| OAuth 换 token 失败 | 自动退 RSS | `channel: Reddit, step: fallback, code: TOKEN_FAIL` |

凭据只用于采集机，**不要拷到展示机**。

# 七、页面构建规范

## 7.1 九分区骨架

页面是竖向单列，从上到下固定九个分区。改版时**不要调整顺序**，它对应「先看结论 → 再看结构 → 最后看明细」的阅读动线。

| 序 | 分区 | 容器 | 作用 |
|---|---|---|---|
| 1 | 侧栏 | `#sidebar` | 三专栏导航 |
| 2 | 标题栏 | `.top-bar` | 页面名 + 口径说明 |
| 3 | 更新条 | `#updateBar` / `#updHist` | 更新到哪天、几个批次、可展开历史 |
| 4 | 总览五卡 | `#kpiRow` | 总声量 / 负面占比 / P0 风险 / 覆盖渠道 / 近 7 日 |
| 5 | 总体概览 | `#pSentiment` + `.grid-2` | 情感结构 + 问题点 Top + 信源结构 |
| 6 | 专项分析 | `#topicGrid` | 按机型特性（KliTek / 多色 / AI 检测…）的八宫格 |
| 7 | 关注维度 | `#dimsBody` | 七大维度的分布与长尾 |
| 8 | 渠道结构 | `#channelBody` / `#chanListBody` / `#matrixBody` / `#compareBody` / `#trendBody` | 占比、覆盖清单、渠道×情感矩阵、竞品、趋势 |
| 9 | 明细区 | `#filters` / `#deepFilters` / `#filterSummary` / `#countLine` / `#cardGrid` | 筛选 + 摘要 + 卡片流 |

两个容易找错的地方：

- **没有独立页脚容器**，口径说明在最后一个面板的 `.pnote` 里
- **没有 `#pager`**，分页控件拼在 `#countLine` 内部渲染

## 7.2 容器与渲染函数

| 容器 | 渲染函数 | 数据来源 |
|---|---|---|
| `#kpiRow` | `renderKPI()` | 用户声量（排除厂商官方） |
| `#sentStack` | `renderStack()` | 有效档 ∩ 排除官方 |
| `#problemsBody` | `renderProblems()` | `applyFilters("problem")` |
| `#sourceBody` | `renderSource()` | `applyFilters("group")`，按渠道组 |
| `#topicGrid` | `renderTopics()` | 全量（专项卡只做筛选入口） |
| `#dimsBody` | `renderDims()` | `applyFilters("dim")` |
| `#channelBody` | `renderChannels()` | **按 `site` 统计** |
| `#chanListBody` | `renderChanList()` | `CHANNEL_MATRIX` + 实际条数 |
| `#matrixBody` | `renderMatrix()` | 10 渠道组 × 五档情感 |
| `#compareBody` | `renderCompare()` | `competitorMentioned` |
| `#trendBody` | `renderTrend()` | 按 `publishedAt` 堆叠 |
| `#filters` / `#deepFilters` | `renderFilters()` | 选项数用 `applyFilters(skip)` |
| `#filterSummary` | `renderSummary()` | 当前已选条件 |
| `#countLine` | `renderCards()` | 命中数 + 分页控件 |
| `#cardGrid` | `renderCards()` | `applyFilters()` |

统一入口 `renderAll()`，顺序固定：

```
更新条 → KPI → 情感结构 → 问题点 → 信源结构 → 关注维度 → 专项八宫格
→ 渠道占比 → 渠道覆盖清单 → 渠道×情感矩阵 → 竞品 → 趋势
→ 筛选栏 → 明细（renderCards 内部再调 renderSummary 与分页）
```

**新增面板必须挂进 `renderAll()`**，否则筛选变化时它不刷新，会停在旧数据。

# 八、交互规范

## 8.1 下钻 = 就地筛选，禁止跳转

点面板条目（问题点 / 维度 / 专题标签 / 卡片标签 / 渠道行）只做一件事：**筛明细**。不滚动、不折叠、不弹层。

唯一反馈是 `flashCards()`——明细区背景闪一次，表示已生效。

**不要使用 `scrollIntoView`**。原实现会跳到明细区并要求用户重新选一次，已被废弃。

## 8.2 所见即所得

面板上的数字必须**恒等于**点击后明细的条数。实现方式是 `applyFilters(skip)`：统计某维度时排除该维度自身条件，保留其它全部筛选。

| 面板 | 调用 |
|---|---|
| 问题点 Top | `applyFilters("problem")` |
| 关注维度 | `applyFilters("dim")` |
| 情感结构 | `applyFilters("sentiment")` |
| 明细区下拉 | `applyFilters(<自己的 key>)` |

任何筛选变化都要走 `renderPanels()`（问题点 + 维度 + 情感结构三者重算）。漏接一个 setter 这条规则就破。

两个必须注意的实现细节：

- **维度与问题点计数必须去重后按条**。一条反馈可能同时提多个维度，按提及次数算会大于实际条数（实测 174 vs 162）
- **情感筛选一旦启用，明细自动限定有效档**。否则点「负面」会混进泛讨论，与面板数字对不上

## 8.3 已选条件只在一处渲染

`#filterSummary` 独家负责「选了什么 + 怎么撤销」：每个条件一个可点 ✕ 的 chip，末尾给清空按钮与命中数。

`#filters` 只负责「怎么选」，**里面不得渲染已选条件**——同一条件在两处出现会被读成两个状态。

清日期条件时必须连 `dateFrom` / `dateTo` / `dateKey` 一起清。

## 8.4 明细区定位条

筛选栏下方单独一条 `#deepFilters`，四个下拉：渠道组 / 专题 / 关注维度 / Top 问题。与上方面板**共用同一份 `activeFilters`**，不是第二套状态。

选项数字同样走 `applyFilters(skip)`。

## 8.5 空态与分页

筛选叠加到 0 条时，文案必须点明是哪个条件导致的，并给出一键清除按钮。不要只写「没有匹配的反馈」。

每页 20 条，按 `publishedAt` 降序。页码用下拉不要平铺（数据会持续增长）。筛选变化自动回第 1 页，靠 `lastFilterKey` 判断，只在 key 变化时重置。

## 8.6 更新条

位置在标题栏下、KPI 上。内容：更新到哪天、固定批次时刻、累计条数、本批新增、已入库批次数、更新历史。

两条禁忌：

- **无入库的日期不出行**——那是「当天没跑批次」，不是「0 条」
- **不显示编造的完成时刻**——`updated` 只到日；要精确到分钟必须由采集脚本写 `updatedAt`，没写就不要硬填

# 九、数据结构契约

改动这一章的任何一条，都会影响去重、推送与统计，**改前先确认影响面**。

## 9.1 核心字段

| 字段 | 说明 |
|---|---|
| `uid` | 幂等主键，`sha1(归一化URL + "|" + 归一化原文片段)[:16]` |

| `date` | 采集入库日（= 运行日） |

| `channel` | 国内 / 海外 |
| `sourceType` | 用户 / 媒体 / 社区综述 / 电商 / 官方 |
| `platform` | 渠道名，**不是子版块** |
| `site` | 站点级名称，**集中度必须按它统计** |
| `collectMethod` | 条目级：auto / search / api / paid / manual |
| `sourceLink` | 原文直链，必须 https 且可访问 |
| `sentiment` | 非常负面 / 负面 / 中性 / 正面 / 非常正面 |
| `topics[]` | 机型特性标签（见 9.3） |
| `dimensions[]` | 七大维度，二级用「一级 - 二级」 |
| `problemPoints[]` | 具体问题点，正面中性可为空 |
| `originalText` | 原文片段（英文保留原文，中文原样） |
| `translation` | 中文翻译 |
| `summaryCn` | 一句话中文摘要，30~60 字 |

| `firstSeenAt` / `lastSeenAt` / `revisedAt` | 时间戳 |
| `mirrors[]` | 同内容在其他平台的转载链接 |

`collectMethod`（条目级事实）与 `CHANNEL_MATRIX.method`（渠道级能力）不同源，**不可互相推导**。

## 9.2 主键规则（最容易被无意破坏）

```
uid = sha1( normalizedUrl + "|" + normalizedText )[:16]
```

URL 归一化：去掉追踪参数（`utm_*` / `ref` / `fbclid` / `gclid` / `si` / `spm` / `share_*` / `from` / `src`）、去 fragment、http 升 https、去末尾 `/`、域名小写。

文本归一化：`originalText` 折叠空白后取前 200 字（为空退回 `summaryCn`）。

**为什么必须带原文片段**：K3 的归并帖一个 URL 承载多条独立反馈，实测 36 条只落在 20 个 URL 上（Makers101 一稿 ×8、什么值得买一帖 ×4）。只用 URL 会把 36 条压成 20 条，16 条永远进不了差集；日后新增内容落在同一帖还会被误判「已见过」而静默丢弃。

由此得出一条硬约束：**`originalText` 参与 uid 计算，禁止改写已有条目的原文**。确需修改必须同步更新 `uid`。

## 9.3 幂等 upsert

命中已有 uid：

- 可刷新：`publishedAt` / `lastSeenAt` / `sourceLink` / `originalText` / `heat` / `mirrors` / `problemPoints` 的新增项
- 不可改写（当 `lock=true`）：`sentiment` / `topics` / `dimensions` / 既有 `problemPoints` / `isP0`

未命中：新增条目，`lock=false`，记 `firstSeenAt`。

`lock=true` 的条目源内容若变化，**只追加 `reviseNotice` 提示人工复核，不得直接改判**。

同内容多平台转载写进 `mirrors[]`，不新增条目，声量只算 1。

## 9.5 文件格式约束（改数据必读）

`creality-k3.html` 里的数据是 **JS 对象字面量，顶层键不带引号**：

```js
const K3_FEEDBACK_DATA = {
  items: [
    { uid:"...", id:"K3-20261020-001", ... },
  ]
}
```

由此带来三条硬约束：

1. **禁止用 `json.loads` / `JSON.parse` 解析**，必须用 Node `vm.runInNewContext` 或括号配平解析
2. **注入后必跑 `_k3_validate.js`**，它会检查字段完整性、重复 id、链接协议、内层裸双引号
3. **`summaryCn` / `translation` / `originalText` 内不得出现未转义的 ASCII 双引号**（P4 闸门）

# 十、口径契约

以下数字口径**不要在没有对齐的情况下改动**，改了会与历史结论、对外汇报、飞书卡片全部对不上。

## 10.1 分析口径 = 有效档

情感类指标（负面占比、情感结构、渠道×情感矩阵）只统计**审核档 = 有效**的条目，并排除厂商官方。

当前：用户声量 421 → 有效档 316 → 负面 57 → **负面占比 18.0%**。按全量算是 14.7%，差在 105 条泛讨论。

## 10.2 泛讨论的处理

泛讨论 = 提问 / 教程 / 公告 / 纯期待，审不出具体问题。当前 105 条。

| 处理 | 规则 |
|---|---|
| 计入总声量 | 是 |
| 计入情感结构 / 负面占比 | 否 |
| 计入问题点与维度 | 否（这批 0 条带问题点、0 条带维度） |
| 出现在明细 | 是，灰底 + 「泛讨论」标，不显示情感标签 |

## 10.3 问题点有两个口径

| 口径 | 算法 | 用途 |
|---|---|---|
| 提及次数 | 一条内多个原始标签归到同类目会重复计 | 议题被说的密度 |
| 涉及条目数 | 去重后每条只计一次 | 议题波及多少人 |

两个都对，回答不同问题。引用时必须写明口径。

## 10.4 热度不等于情绪浓度

提得最多的议题未必最不满。实测「能力未经第三方验证」提及最多，但中性 6、正面 1、负面仅 5（42%）——那是观望。

负面浓度真正高的是：价格与首发信心 71%、软件配套滞后 67%、换色换头耗时长 63%。

## 10.5 集中度按 site 统计

`platform` 有「Makers101（引 r/Creality）」这类同源变体，按它算会把一个来源拆成两个。Top1 / Top2 / HHI 一律用 `site`。

## 10.6 跨期比较必须固定信源

总负面率会被渠道结构污染：每接入一个中性内容为主的渠道，整体负面率就「改善」一次。

实测按批次：10-13 72.2% → 10-14 29.0% → 10-15 2.0% → 10-16 0%。不是产品变好，是 YouTube 评测灌进来冲淡了分母。

页面上「信源集中度」必须标注「反映采集能力，不等于用户真实分布」。当前 YouTube 321 条占 76.1%，是采集能力的结果。

## 10.7 问题点归并 16 条（顺序即优先级）

```
换色/换头实际耗时长 · 噪音大/分贝无实测 · 软件与配套滞后 · 无封箱/无主动仓温
售后响应与保修 · 价格与首发信心 · 做工与用料细节 · 头数/尺寸/配件局限
能力未经第三方验证 · 抄袭与法律争议
交付与履约 · 信息透明度与沟通 · 宣传口径与实测落差 · 喷嘴与耗材规格
竞品对比与定位 · 品牌与品控信任
```

`normProblem()` 是「第一个命中即返回」，所以：

- **关键词越宽的类目越靠后**（「竞品对比」含最宽的 `U1` / `K2`，放倒数第二）
- **语义重叠要合并而不是新增**（废料并入换色、加热仓 / Top Cover 并入无封箱）

页面 `normProblem` / `topDims` 与引擎 `norm_problem` / `top_dims` 是**两套独立实现，改一处必须同步另一处**。

# 十一、运维手册

## 11.1 每日巡检

| 检查 | 方法 | 正常表现 |
|---|---|---|
| 采集是否跑完 | `tail logs/collect.log` | 无 Traceback，有渠道条数统计 |
| 候选池是否非空 | 看 `_k3_candidates_*.json` | 工作日 3~8 条 |
| 注入是否成功 | 页面「更新条」 | 显示当日批次 |
| 校验是否全绿 | `node _k3_validate.js` | 无异常输出 |
| 页面是否可访问 | 浏览器打开 | 正常渲染，无空白 |

## 11.2 故障排查表

| 现象 | 根因 | 处置 |
|---|---|---|
| B 站采集全 412 | 未预热 cookie 就连续请求 | 先 GET `https://www.bilibili.com/` 取 `buvid3`/`b_nut`，之后 3s 间隔；**不要靠降频解决，越重试封越久** |
| Reddit 403 / 429 | 出口 IP 被限 | RSS 间隔 ≥6.5s，429 后退避 20s。**日更里 Reddit 403 属已知封锁，不要当失败告警** |
| 页面打开空白 | JS 语法错误或数据未注入 | F12 看 console；跑 `_k3_runtime.js` 定位；检查是否误用 `json.loads` |
| 面板数字与明细对不上 | 某 setter 未接 `renderPanels()`，或维度按提及次数计 | 检查 `applyFilters(skip)`，确认去重后按条 |
| `--print-uid` 报碰撞 | 两条用同一 URL + 同一片段，或原文被改写 | 查 `originalText` 是否被改；碰撞非零不得发布 |
| 页面推上去变空文件 | 单次内联内容超体积上限 | 走分块/独立文件上传，不要内联进一次请求 |
| 新增渠道全落「其他」 | 分组规则未同步 | 三处必须同改：页面 `groupOf()`、引擎 `GROUP_RULES`、文档渠道表 |
| 译文与原文错位 | 重跑了归一化脚本 | 补字段类脚本只加字段，**不重跑归一化**（重跑会改 `originalText`） |
| 页面样式错乱 | 行尾符被改成 CRLF | 统一 LF；构建/诊断工具可能回写 CRLF，跑完要转回 |
| 详情页 404 但文件存在 | 静态服务大小写或路径不一致 | 确认 URL 与实际文件名完全一致 |

## 11.3 回滚

发布前必须备份。出问题的回滚顺序：

1. 停掉定时任务，防止再次覆盖
2. 从 `backup/` 取最近一版覆盖回去
3. 同步到展示机，确认页面正常
4. 定位问题，在采集机修好后重新走完整流水线

单文件页面的好处是回滚成本极低——一个文件拷贝即可。

## 11.4 校验脚本的作用（不要跳过）

| 脚本 | 校验内容 | 不跑的后果 |
|---|---|---|
| `_k3_validate.js` | 字段完整性、重复 id、链接协议、裸双引号 | 坏数据进页面，渲染时报错或显示 undefined |
| `_k3_runtime.js` | 假 DOM 跑真实渲染函数，含下钻、筛选、分页 | 交互坏了但页面「看起来正常」，用户点了没反应 |
| `_k3_feishu_delta.py --print-uid` | uid 唯一性 | 条目被静默覆盖或推送漏发 |

三个脚本全部需要在**发布前**跑，全绿才发布。
